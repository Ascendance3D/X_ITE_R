# X_ITE_R browser API — supported and unsupported

Reference: X_ITE 16.5.0 (`oracle/x_ite-pin`, commit `34cdf9f97`). Names are X_ITE's.
"Compared" means a browser test checks the value against a pinned X_ITE recording: `oracle/web-browser-01-baseline` (runtime 01), `oracle/web-browser-02-baseline` (runtime 02, 30 cases), `oracle/web-browser-fallback-01-baseline` (10 cases) or `oracle/web-browser-loadurl-01-baseline` (21 cases), `oracle/web-browser-options-01-baseline` (browser options, properties, rendering properties, print; 9 cases), `oracle/web-browser-attributes-01-baseline` (canvas attributes and the options they set, contentScale, maximumFrameRate, update; 10 cases) or `oracle/web-browser-entry-01-baseline` (X3D entry points and `captureStream`; 12 cases).

This is a small subset. It is not full X_ITE API compatibility.
The Rust engine does all X3D work: parsing, events, sensors, picking, navigation and rendering. The JavaScript adapter only forwards page events and calls.

### Resource loading

The world of `loadURL`, Inline, ImageTexture, EXTERNPROTO, FontStyle and FontLibrary font files, MovieTexture, AudioClip and BufferAudioSource files load with the page's `fetch` (`cache: "default"`, an `AbortSignal`), without blocking the page. A `data:` URL is decoded by the engine, with no request, as the browser's `fetch` decodes it for every kind of file: `;base64` in any letter case, percent escapes, and a fetch error (`TypeError: Failed to fetch`) for base64 that does not decode. Raw tab, LF and CR characters follow Chrome 156: they are kept (as `%09`, `%0A`, `%0D`) when the URL starts with `data:` in any letter case, after any leading tabs and newlines, and removed otherwise (a leading space, a tab in the scheme), as the URL standard removes them in every other URL. Chromium 151 kept them only after an exact lower-case `data:`. A world or Inline document that is not base64 is read as X_ITE's FileLoader reads it: only a lower-case `;base64` is base64, and one malformed escape keeps the text undecoded.
The engine runs every fallback chain, also the world's; the JavaScript adapter only prints the engine's messages.
A world waits for its loads before it replaces the current world, like X_ITE's scene `loadCount`; the current world runs meanwhile.
Compared: relative URLs, HTTP errors (`Error: Not Found`), data that is no X3D or image, MFString fallbacks in order, cross-origin requests without CORS (`TypeError: Failed to fetch`), EXTERNPROTO fallbacks and waiting, and the console messages and their levels.
Tested: requests that end after a newer `loadURL`, after `dispose ()` or after the element left the document never reach another world.
Compared (`tests/browser/fallback01.test.mjs`): after a candidate that downloads but does not load (no parser takes it, it does not parse, an image does not decode, a glTF buffer fails), the next candidate is fetched then, in order, with X_ITE's messages; a candidate after the one that loads is never fetched. The external buffers of a glTF file are requested together and resolve against the glTF file. A load waits for its responses and never blocks the page.
Compared (`tests/browser/loadurl01.test.mjs`): the candidates of the world-level `loadURL` and their messages, also when a newer `loadURL`, `replaceWorld` or `dispose ()` comes while one is in flight; a FontStyle font file that is missing or no font, then one that loads; a MovieTexture GIF or video that fails, then a GIF; an AudioClip file that does not decode, then one that does, and when none does. Each of these waits for the response of the next candidate, also when it is held.

### Sound

Compared (`tests/browser/sound01.test.mjs`, `oracle/web-browser-sound-01-baseline`, issue #140): an AudioClip that plays through a Sound node. The audio graph of the engine's Web Audio port (`x3d-runtime/src/sound`) has the same nodes, channel settings, gains, buffer, loop attributes, `start` arguments and connections as the Web Audio graph of X_ITE in the page. The engine gives this graph to tests as JSON (`audioGraph ()` of the wasm object, `Symbol.for ("X_ITE_R.engine")`).

Also compared in the same suite: a clip stopped by `stopTime` (`isActive` FALSE, the source stopped); `loop` turned off while it plays (the clip ends); the order of the `isActive`, `isPaused` and `duration_changed` events over start, pause, resume and the end; an AudioClip whose url does not load (the console messages, the fields and the graph); a world replaced while the clip plays (the source leaves the graph, the page keeps its context); and the Sound fields `intensity`, `location` and `spatialize` (the gains of the graph).

The page makes an `AudioContext` when the first Sound node of a world makes the engine's audio context (X3DSoundContext.getAudioContext), and calls `resume ()`, as X_ITE does. It calls `resume ()` again while the context waits: on the canvas events of X_ITE's list (a user gesture unlocks it under the browser's autoplay policy) and when a sound source starts or resumes its media (X3DSoundContext.startAudioElement). Before each frame the engine takes the context's `currentTime` as its audio clock; the engine keeps the latest one, and a world that `replaceWorld` installs while the canvas is detached starts with it, not with 0. The same `AudioContext` serves every world of the browser, and `dispose ()` closes it (once; an `AudioContext` of the page's own is never touched). So a clip that does not loop ends when the audio clock passes its duration, a paused clip resumes at its position, and while the autoplay policy holds the context, the clock and the clips wait, as in X_ITE. Nothing is connected to the page's context yet: the page plays no sound.

Also compared with a pinned recording (`tests/browser/sound03.test.mjs`, `oracle/web-browser-sound-03-baseline`, 23 cases, 15 identical X_ITE 16.5.0 runs in three processes): `Mute` and `SoundIntensity` (the gain of the sound destination after each change, and set before the world loads), an AudioClip's `pitch` (also changed while it plays; negative gives rate 0), the Sound ranges (`minFront`/`maxFront`, `minBack`/`maxBack`, on the limits, spatialized), `priority` (stored; the graph does not change), the audio listener (default, ListenerPointSource fixed and tracking the view), the page's AudioContext over a load, a gesture, two `replaceWorld` calls and `dispose ()`, an AudioDestination node, and a world replaced by another playing world. The start offset of the replacement clip is a race in X_ITE (0 or a few samples), so that field is not compared. `tests/browser/sound02.test.mjs` keeps the checks of the engine against values worked out from the X_ITE source, and the checks of the page's clock and `dispose ()`. These tests read the graph; nothing in them is heard.

**Unresolved gap (audible output).** The `audible*` cases of sound03 put a tap on the page's AudioContext destination. In X_ITE the tap measures the clip and the OscillatorSource (RMS 0.22 for the clip), and measures nothing with `Mute` on. In X_ITE_R it measures nothing: the engine renders into its own Web Audio port and connects no node to the page's context, so a page of X_ITE_R is silent. The comparison lists this as a known difference; the issue stays open.

## Known differences inside the supported part

Each difference below is listed in `KNOWN_DIFFERENCES` of `tests/browser/api.test.mjs` or `tests/browser/runtime02_harness.mjs` when a compared case shows it.

- Field callbacks run after the frame that processed their events, not inside its event cascade. A callback gets the value of its event, as in X_ITE; a field it sets sends its event in the next frame, where X_ITE's goes on in the same cascade. A callback that throws is an uncaught page error, as in X_ITE: the callbacks and events after it never run, and the engine processes no event again (the frames go on). Registering a callback while another runs, and removing one in place, follow X_ITE's Map semantics. Compared in `tests/browser/fields04.test.mjs`. Refs #137.
- A node can only be assigned to a field of a node of the same world (a scene of `createX3DFromString` is a world of its own). X_ITE allows it: the node keeps its own scene, and the field holds it. X_ITE_R refuses the assignment, prints the warning `X_ITE_R: a node can only be used in the world it belongs to.`, and leaves the field as it was. The same holds for a node list (`MFNode`), which is refused as a whole, and for the scene's `rootNodes` (`push`, assignment, `addRootNode`, `setRootNodes`) with a node of another world: the warning is printed, the page's field keeps the value it was given, and the world keeps the root nodes it had (`s04`). As in X_ITE, an `SFNode` setter keeps a plain JavaScript property when it fails, so the page reads the node back from that property. The text forms and the field value do not show it. An operation on the field after a refused one goes on (the engine keeps its old value, and a text form shows it, see `s13`). A node of a replaced world is refused as stale, where X_ITE keeps it usable. Refs #137, #145. Compared in `tests/browser/fields03.test.mjs` (12 compared scenarios; the cross-scene `ROUTE` scenario, s06, is compared in `routes01.test.mjs` with `addRoute` of #135).
- A route belongs to one world (the engine runs one world at a time). X_ITE puts no limit on the scenes of the nodes of a route: `scene .addRoute (nodeOfThisScene, ..., nodeOfAnotherScene, ...)` works and carries events between the scenes, and `other .addRoute (nodeOfThisScene, ...)` puts a route of the other scene on nodes of this one. X_ITE_R refuses each of these (`addRoute`, `getRoute`, `deleteRoute`, `browser .addRoute`) with the warning `X_ITE_R: a node can only be used in the world it belongs to.` and the same error as a node of another world in a field, so a page that routes between scenes does not work. This closes the deferred cross-scene `ROUTE` scenario (s06) of `fields03`: compared in `tests/browser/routes01.test.mjs` (`routesApi.crossScene`). X_ITE also runs the events of a scene that is not the world (a `createX3DFromString` scene), so a route inside such a scene carries events; X_ITE_R steps only the world, and the routes of another scene carry none (`routesApi.scenes`, `events`). The routes of a replaced world: `routes`, `addRoute` and `getRoute` of its `X3DScene` throw the stale-world error, where X_ITE keeps them usable (`routesApi.browser`). `X3DScene .toVRMLString ()` is not supported, so a world's `ROUTE` statements cannot be printed. Refs #135.
- The text forms of nodes and scenes take no options: `toVRMLString ()`, `toXMLString ()` and `toJSONString ()` (of an `X3DScene` too) print with X_ITE's default generator options, and the options object (`style`, `indent`, ...) is ignored. `toString ()` needs none: X_ITE's `X3DNode .toStream` prints `TypeName { }`.
- `X3DField .fromVRMLString` and `fromXMLString` take an `X3DScene` of this adapter as `scene`; the nodes of the value are made in that scene's world. `fromJSONString` calls `fromVRMLString`, as in X_ITE. A value read without a scene works for every type that needs no node, in a page where the engine is loaded (use `browser .ready ()`). Before that it throws `X_ITE_R: the engine is not loaded yet; wait for browser .ready ().`.
- Removing the element from the document stops the frame loop and releases the buttons and touches that are down; adding it again restarts the loop. X_ITE keeps drawing, and its document `mouseup` listener releases later.
- A `pointercancel` (for example a touch the browser takes for scrolling) releases the touch: the sensor or the viewer ends its drag. X_ITE has no `touchcancel` handler, and its TouchSensor stays active.
- After the element is removed and added again while the pointer did not move, a TouchSensor stays `isOver`. X_ITE ends `isOver`, because its release checks the pointer against the detached canvas (an empty rectangle).
- A hidden page (`visibilityState` hidden) cancels the frame loop, and showing the page starts it again. X_ITE keeps its loop scheduled and relies on the browser to pause `requestAnimationFrame`.
- A URL is requested once per world, also when several nodes use it. X_ITE sends one request per node (the HTTP cache may answer).
- A `data:` URL whose base64 does not decode gives the same message as in X_ITE, without Chromium's own `Failed to load resource: net::ERR_INVALID_URL` line before it: X_ITE_R makes no request for it.
- An empty document (`data:model/vrml,`, or an empty file) is an empty world. X_ITE rejects it; in the recording page it fails with `ReferenceError: CharLS is not defined` (DICOMParser).
- An image that does not decode fails with `Couldn't load image '<file URL>': error.`. X_ITE names the blob URL of the data.
- A world with an Inline whose glTF file has a buffer that fails finishes loading. In X_ITE the world never does, also when the Inline loads its next candidate: GLTF2Parser does not remove the failed buffer from the scene's loading objects, so `loadURL` never settles.
- A newer `loadURL` ends the loads of the older world. X_ITE's Inline FileLoaders of the older world go on: a candidate that responds after the replacement and does not parse is reported, and the next candidate is fetched.
- After `dispose ()` X_ITE draws a frame and throws `Couldn't create frame buffer.`; X_ITE_R's frame loop has stopped.
- `loadURL` rejects with `Loading of X3D file aborted.` after `dispose ()`. X_ITE's never settles. X_ITE's `dispose ()` also fires `shutdown`; X_ITE_R's fires no event.
- A scene does not wait for its FontStyle font files or for an AudioClip's decode: it can go live while a font file or the next audio candidate is still in flight. The FontStyle and the AudioClip wait for their responses and complete later. In X_ITE these nodes hold the scene's loadCount, so `createX3DFromString` and `loadURL` settle only after them.
- An Anchor or `loadURL` never opens a `javascript:`, `vbscript:`, `ecmascript:`, `vrmlscript:` or `data:` URL in a window or as the page location, in any letter case; it logs `X_ITE_R: Anchor URL '...' was not opened.`. X_ITE checks for script URLs in lower case only and opens the others. A new window opens with `noopener`.
- The browser fires its first `initialized load` (the empty world) when the engine is ready, which is asynchronous (WebAssembly and the WebGPU device). Use `browser.ready ()` or wait for the `load` of your world. X_ITE fires nothing for its first empty world, so the events of an element made by `X3D.createBrowser ()` start with this `initialized load` in X_ITE_R and are only the world's own in X_ITE (also with a URL, a bad URL and a wrong argument; recorded in `entryPoints.createBrowser*`).
- A node handle belongs to one world, and so does an `X3DScene` object. After the world is replaced (also by an Anchor), using an old node or scene throws `X_ITE_R: the node belongs to a world that was replaced.`; `currentScene` gives the new scene. In X_ITE the old objects stay usable but are no longer the world.
- The engine releases a node when its scene is disposed (an Inline unloads) and nothing refers to it any more, and a later node can take its id. Using a node object of a released node then throws `X_ITE_R: the node was released; it is no longer in the world.`, and its field callbacks get no more events; a node that takes the id is a new node object. In X_ITE the old node object stays usable.
- Field values the page assigns are checked: data of the wrong shape (too few components, a number for a boolean) or a node that is not in the world throws instead of being filled in.
- `ready ()` is not an X_ITE name. X_ITE starts synchronously and needs no such call.
- The `layerNode` of the viewpoint functions is a node of the current world: a layer node of another world, or of a replaced one, counts as no layer node (the active layer; `bindViewpoint` throws its layer error). X_ITE casts a node of any scene.
- Sound: after `replaceWorld`, X_ITE keeps the page's audio context with the destination node alone in its graph; X_ITE_R's audio engine goes with the replaced world, so `audioGraph ()` gives nothing until a Sound node of the new world makes one. The page's AudioContext is the same in both (compared). `dispose ()` closes the page's AudioContext in X_ITE_R and leaves X_ITE's running (sound03 `lifecycle`); an AudioDestination node feeds the engine's destination in X_ITE_R and a MediaStream destination in X_ITE (sound03 `audioDestination`).
- Sound: the AudioDestinationNode of the engine's Web Audio port has `numberOfOutputs` 1 (the Web Audio specification and the web-audio-api crate); Chromium's has 0. X_ITE shows its "no sound" button while the AudioContext waits for a gesture; X_ITE_R has no such button. A MovieTexture does not make the page's AudioContext (X_ITE's does), and AudioDestination and StreamAudioDestination media were not compared.
- Canvas attributes: see "Canvas attributes" below. `baseURL` and `extensions` have no effect.
- Browser options the renderer does not honor: `setBrowserOption` stores a value that `getBrowserOption` reads back. Three options drive the page (see "Canvas attributes"): `ContentScale`, `MaximumFrameRate` and `AutoUpdate`. The other options are stored only, because the WebGPU renderer and the wasm layer expose nothing to apply them to, or the feature does not exist in the browser build: `SplashScreen`, `Dashboard`, `Rubberband`, `EnableInlineViewpoints`, `Antialiased` and `Multisampling` (the renderer's sample count is fixed at start; `Renderer::set_sample_count` is not exposed to JavaScript), `TextureQuality`, `PrimitiveQuality`, `QualityWhenMoving`, `Shading`, `MotionBlur`, `AlwaysUpdateGeometries`, `Cache`, `ColorSpace`, `ContextMenu` (no context menu), `Debug` (no debug keys), `Exposure`, `ToneMapping` and `DisplayColorSpace` (no such renderer setting is exposed), `Gravity`, `LoadUrlObjects`, `LogarithmicDepthBuffer` (read back by `getRenderingProperty`, no effect on depth), `MetadataReference`, `Mute` and `SoundIntensity` (they set the gain of the engine's sound destinations, but the browser build has no audio output), `Notifications` (none are shown), `OrderIndependentTransparency`, `StraightenHorizon`, `TextCompression`, `Timings` (no timings display), `WallFriction` and `XRSessionMode` (no XR). X_ITE also keeps `PrimitiveQuality`, `Rubberband`, `StraightenHorizon`, `TextureQuality` and `Timings` in `localStorage` between pages; X_ITE_R does not.
- `createX3DFromURL (url, node, event)` and `createVrmlFromURL` with a node of a scene that is not the world (a scene of `createX3DFromString`, `createScene` or the promise form, which has no frames of its own in X_ITE_R): the scene of the url loads as a scene of its own, and the field refuses its nodes (see the known difference of a node of another world above), with the warning `X_ITE_R: a node can only be used in the world it belongs to.`; the field keeps its value. For a node of the world the nodes go into the field, as in X_ITE. Not compared: the recorded cases use nodes of the world.
- `browser .supportedComponents` has the Annotation component (level 2) after X_ITE's 39, so 40 components: X_ITE 16.5.0 ships its classes but does not register it, and X_ITE_R does (REA batch 04 owner decision, `crates/x3d-scene/src/nodes.rs`). Compared in `supportedLists` (the known difference of `tests/browser/runtime02_harness.mjs`).
- `browser .addSupportedProfile`, `updateSupportedProfile`, `removeSupportedProfile` and the same for components are not supported: the supported lists are those of the pinned X_ITE. The `toXMLString ()` and `toJSONString ()` of `ProfileInfo`, `ComponentInfo` and their arrays are not supported. The `providerURL` of an external component is `assets/components/<name>Component.js` next to `x_ite_r.mjs` (X_ITE: next to its own script); the file part is compared.
- The profile and components of a scene of `createScene` are kept by the page's `X3DScene` object; the engine's scene has neither (no text form prints them, since `X3DScene .toVRMLString ()` is not supported).
- `createVrmlFromString` before the first world (the page's empty one): the nodes belong to a scene of their own, which they keep alive, and not to the world (there is none to make them in). After a `loadURL` or `replaceWorld` they are the world's. The nodes of a world that was replaced are stale (see the known difference of a replaced world above).
- `importDocument (htmlElement)`: X_ITE's HTMLParser reads the HTML element of an `<X3D>` in a page (tag and attribute names are case-insensitive there); X_ITE_R rejects an `HTMLElement` with `X_ITE_R: Browser.importDocument: an HTML element is not supported; ...`. It takes the XML string, an `XMLDocument` or an XML element (serialized and parsed by the engine's XML parser). The DOM integration of #146 is not here.
- `importJS`, `importDocument`: the scene's `worldURL` is the page's URL, like X_ITE's. Its Scripts run only when the page lets them (see "Script nodes").

## Script nodes

**Status: PARTIAL.** (This entry replaces "Script nodes: not implemented".) Script nodes run in the browser build, off by default. They are not COMPLETE: the kept differences below are open, and the Script life cycle cases of `tests/browser/scriptlife01.test.mjs` list the ones that a pinned recording shows.

Refs #133. A Script node runs in the page's own JavaScript engine, as in X_ITE. The engine and its Script implementation are the native viewer's (`crates/x3d-script`, the X_ITE 16.5.0 prelude), so field access, routing, event order and the Script lifecycle are the same.

**Security.** A Script runs with the privileges of the page. It can read and change the document, call the page's functions and send requests as the page. X_ITE_R gives no isolation from the host page; treat Script code as code of the page.

**The switch.** The Scripts do not run by default. The page lets them run with the `scripts="true"` attribute of `<x3d-canvas>`, which is read when a world starts (`loadURL`, `src`, `createX3DFromString`, `createX3DFromURL`, `importJS`, `importDocument`). Any other value, or no attribute, keeps them off: a Script then logs `Couldn't load URL ... no script engine`, and the rest of the world runs. The attribute does not check where a Script's code comes from: a world from another server, an Inline or an external `.js` file runs with the page's privileges as well. Set it only for content you trust.

**Content Security Policy.** The Script engine evaluates source text with `new Function` and `eval`, so a page that lets Scripts run and has a Content Security Policy needs `'unsafe-eval'` in its `script-src`. Give that only to the page that embeds X_ITE_R for trusted content, not to unrelated applications. X_ITE_R itself needs only `'wasm-unsafe-eval'` for its WebAssembly. Without `'unsafe-eval'` the Scripts of a world do not run: the engine logs `X_ITE_R: the Scripts of this world cannot run: EvalError: ...`, each Script logs `no script engine`, and the rest of the world runs.

Compared with pinned X_ITE 16.5.0 in `tests/browser/script01.test.mjs`: the 8 synthetic Script worlds of `oracle/synthetic-x6` (scene text and console, `oracle/synthetic-x6-baseline.json`) and the 11 Script cases of `oracle/web-browser-script-url-01-baseline`, including what the Script did. The same file tests the default, the policy, the lifecycle and event order, and the page's `rootNodes` field when a Script changes the root nodes.

Kept differences from X_ITE:

- `Browser.print` and the Script's console messages reach the page's console when the engine returns from the event or frame, not during the Script's call. The page's field callbacks (`addFieldCallback`) print in X_ITE's order: the lines made before an event, then its callbacks, then the lines its routes make (compared, `scriptLife.events`). A callback that changes the world still runs after the engine call, not inside the route chain. The same order holds for an observed input of a Script (its handler prints first, then the page's callback) and for the `rootNodes` event (it comes in its turn, after the lines of a handler that changed the root nodes, and after the lines of the Scripts' own `rootNodes` callbacks). Checked in `script01.test.mjs` (`order.*`) against pinned X_ITE 16.5.0 from a one-off run, with no new baseline. If a Script's `rootNodes` callback and another event print in one cascade, the page's `rootNodes` event follows both.
- The promise jobs of a Script run when the page's JavaScript stack is empty, after the engine's call. A change they make to a field object reaches the engine at its next call.
- A function that a Script left in the page and that is called after its world was replaced throws `X_ITE_R: the Script's world is gone.` X_ITE keeps the old world's nodes usable.
- There is no time limit: a Script that does not return stops the page, as in X_ITE. The native viewer stops it after 10 s.
- There is no case of `importJS` or `importDocument` with a Script that runs: the Script switch applies to them, but no test compares them with X_ITE.
- Open gap: a Script that changes the world from a page callback, and the output of an element that is disposed, are not compared.

Compared with pinned X_ITE 16.5.0 in `tests/browser/scriptlife01.test.mjs` (12 cases, synthetic worlds, `oracle/web-browser-script-life-01-baseline`, recorded 5 times with identical values): `initialize` (events sent from it, the order of the Scripts, `directOutput`), the events of Script fields (eventIns, eventOuts, routes, an interpolator, the page's events, several events in one task), `eventsProcessed`, `shutdown` when the Script's code is replaced and when the world is replaced, Script errors (in `initialize`, a handler, `eventsProcessed`, `shutdown`, at the top level, a syntax error, a thrown string or object), and the `rootNodes` of `Browser .currentScene` in a Script (a live `MFNode`, the same object on every read: `push`, `splice`, `assign`, `addRootNode`, `removeRootNode` and `setRootNodes` change the world, a callback runs once when the world starts and after each change, before the page's callbacks) and the callbacks of the page. A node that is a root node and a Script field value prints once with `DEF` and `USE`: the page's text forms read the clone counts as they are now. The cases that differ are listed in `KNOWN_DIFFERENCES` (`tests/browser/runtime02_harness.mjs`), with X_ITE's value checked against the recording:

- `shutdown` follows X_ITE 16.5.0 (compared, `scriptLife.shutdown`, `scriptLife.errors`): the browser build does not call it when the world is replaced or the element is disposed, and calls it when the Script's code is replaced. The native viewer still calls it (ISO/IEC 14772-1 4.12.3).
- X_ITE 16.5.0 throws `array[i].set is not a function` for a change of the root nodes while a Script is a root node itself. The cases keep the Script in a Group, so X_ITE_R's behavior there is not compared.

## Canvas attributes

Compared with the pinned X_ITE in `oracle/web-browser-attributes-01-baseline`. An attribute sets its browser option when the element starts (the parser's attributes) and on every change, with X_ITE's rules: `true` and `false` are the only boolean values (any other text, also `TRUE` and the empty text, is the default of the attribute), a string attribute that is empty gives its default, a removed attribute gives that default as well (not the default of the option), and the number attributes (`exposure`, `maximumFrameRate`, `multisampling`, `contentScale`) pass the text to the option's number coercion (`x` gives NaN, `multisampling` gives an integer). The options never write an attribute back: setting an option leaves the attribute as it was, and a later attribute change replaces the option's value.

| attribute | option | effect |
| --- | --- | --- |
| `contentScale` | `ContentScale` | the framebuffer size is the CSS size times the option (`auto` is -1, the device pixel ratio, followed in every frame); 0, a negative or a NaN value gives a 1 x 1 framebuffer, like X_ITE. Setting the option does the same as the attribute. A stopped browser (see `update`) applies a new size when it starts |
| `maximumFrameRate` | `MaximumFrameRate` | a frame sooner than 1 / max (rate, 1) seconds after the last processed one is skipped whole (events and drawing), like `X3DTimeContext.advanceTime`; NaN does not limit. The interval is measured with the frame timestamp of `requestAnimationFrame` (X_ITE: `Date.now ()`): X_ITE draws on demand, and this browser draws every frame, where two `Date.now ()` values can be closer than the frame period |
| `update` | `AutoUpdate` | `auto` sets the option to true; any other value sets it false and starts (`true`, removed, or any text other than `false`) or stops (`false`) the browser. A stopped browser is not live (`endUpdate ()`): its TimeSensors and the like pause and the input held at the stop is let go; the events of the page and the routes still run, and `loadURL` and `replaceWorld` still finish. With `AutoUpdate` true a canvas that is hidden or scrolled out of view stops, and starts again if it was running before (setting the `AutoUpdate` option does the same watching as `update="auto"`). `update="auto"` on a stopped browser leaves it stopped |
| `oninitialized`, `onshutdown` | | the text becomes the event handler of the element, called before the event is dispatched |
| `antialiased`, `cache`, `colorSpace`, `contextMenu`, `debug`, `displayColorSpace`, `exposure`, `logarithmicDepthBuffer`, `multisampling`, `notifications`, `orderIndependentTransparency`, `splashScreen`, `textCompression`, `timings`, `toneMapping`, `xrSessionMode` | the option of the same name | the option is set and read back, compared; nothing else happens (see "Browser options the renderer does not honor") |
| `baseURL` | | not implemented: X_ITE sets the base of the relative URLs (`browser.baseURL`); X_ITE_R's `baseURL` is the page's |
| `extensions` | | not implemented: X_ITE observes it and has no effect on options either |
| `src`, `url` | | load the world (supported) |

The `update` attribute and the `AutoUpdate` option call `beginUpdate` and `endUpdate` (see the table of the browser functions): a stopped browser is not live. The introspection `browser [Symbol.for ("X_ITE_R.frameLoop")]` also reports `processed` (the frames not skipped) and `live`.

## Not implemented

- `getUserViewpoints` and the other X3DBrowserContext functions.
- `toVRMLString` and the other stream functions of the browser.
- Most rendering properties: `getRenderingProperty` throws `X_ITE_R: the rendering property '...' is not implemented.` for `Shading`, `Antialiased` (and its alias `AntiAliased`), `ContentScale` and `Multisampling`, which X_ITE derives from the options and the context (`Shading` is the mapped name, `POINTSET` gives `POINT` and an unknown name `GOURAUD`; `Multisampling` is clamped to the context's samples; `Antialiased` is true while the context is multisampled; `ContentScale` is the scale in use), and for the properties of X_ITE's WebGL context: `MaxTextureSize`, `TextureUnits`, `MaxLights`, `ColorDepth`, `TextureMemory`, `MaxAnisotropicDegree`, `MaxSamples`, `PixelsPerPoint`, `SoundDestinations` and `XRSession`. The WebGPU renderer has no such values.
- `importDocument (htmlElement)`: the DOM integration of #146, see the known differences.
- Splash screen, context menu, notifications, timings, XR.
- Sound output: a page hears nothing. The engine's Web Audio port builds the same audio graph as X_ITE (compared, see "Sound" below), but it does not render into the page's AudioContext.
- MovieTexture frames are not decoded (the engine's `movie_load`): a GIF or PNG that downloads, or a `.webm`, `.ogv`, `.ogg`, `.mp4` or `.m4v` file that downloads, counts as loaded. X_ITE decodes the GIF or APNG and plays the video in a `<video>` element; a video that does not play fails there and the next candidate is tried. X_ITE_R tries the next candidate only after a video name it does not take as playable.
- A `replaceWorld` while a `loadURL` waits for its Inline and texture responses does not stop that load: like X_ITE, the older world then replaces the newer one.

## Graphics

The renderer is WebGPU only (wgpu 30 `Backends::BROWSER_WEBGPU`). There is no WebGL renderer.
Before it makes the renderer, the engine checks the adapter's limits against what the renderer needs. A shortfall stops the start with `X_ITE_R cannot start: ...` in the element and names the limit.
A lost device (driver reset, GPU process crash, a background tab the browser reclaims) stops the frame loop, calls the `CONNECTION_ERROR` callbacks and shows `X_ITE_R stopped: the WebGPU device is lost.`.

WebGPU compatibility mode (`requestAdapter ({ featureLevel: "compatibility" })`, for devices with OpenGL ES 3.1 class GPUs) is not used. wgpu 30's `RequestAdapterOptions` has no `featureLevel` field and its WebGPU backend always requests a core adapter, so the engine cannot ask for one. This is the blocker until wgpu has the option.

## Mobile support

Pointer Events give mouse, pen and touch input; the engine gets touch as X_ITE's TouchEvent handlers do. Rotation and resize change the framebuffer on the next frame.

The WebGPU column is the vendors' published state as known in mid-2026; this lane did not verify it on devices.

| browser | WebGPU (vendor documentation) | state |
